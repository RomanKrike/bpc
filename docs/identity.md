# User and Device identity

Stage 3 adds a controller-owned identity layer for BP Connect without changing
the BPC transport cryptography.

~~~text
User password authentication
          |
          v
short-lived login credential
          |
          v
Device registration + Ed25519 proof-of-possession
          |
          v
short-lived device access credential + rotating refresh credential
          |
          v
existing WireGuard + WGShim data plane
~~~

The password is an authentication factor. It is never a WireGuard, WGShim,
Node, or Device encryption key.

## User model

Controller state contains one record per User:

~~~text
id
username
password_hash
enabled
created_at
~~~

Passwords are hashed with Argon2id. Plaintext passwords are never persisted,
logged, put into prepared client executables, or sent to Gateway transport
services.

User records live only under the Controller control-plane state directory.
Gateway/WGShim services do not receive the password database.

Administration:

~~~bash
bpc user add roman
bpc user disable roman
~~~

User add reads the password without placing it in the process command line.
For automation, --password-stdin is available.

Disabling a User invalidates access/refresh credentials and disables owned
Devices.

## Device model

New Device records contain at least:

~~~text
id
user_id
name
public_key
created_at
last_seen
enabled
revoked_at
~~~

The Device Ed25519 private key is generated by BP Connect and remains only in
the local protected client state. The Controller receives only the public key.

The existing per-device WireGuard and WGShim credentials remain separate
transport credentials. Device identity does not replace or derive those keys.

Administration:

~~~bash
bpc device list
bpc device revoke <DEVICE_ID_OR_UNIQUE_NAME>
~~~

Revocation marks the Device disabled/revoked, invalidates current access and
refresh credentials, removes any Stage 2 static-token index, removes the WGShim
relay key, and removes the WireGuard peer.

A revoked Device public key cannot silently register again after a new password
login. A new Device identity must be generated and explicitly registered.

## Authentication API

### Login

~~~http
POST /v1/auth/login
~~~

A successful login returns a short-lived, login-scoped opaque access
credential. It exists only to authorize Device registration and is consumed
after registration.

Default access lifetime: 10 minutes.

### Device registration

~~~http
POST /v1/devices/register
Authorization: Bearer <login-access>
~~~

BP Connect locally generates an Ed25519 Device keypair and a WireGuard keypair.
The registration request sends public keys and an Ed25519 proof-of-possession
over HTTPS. The Device private key is never sent to the Controller.

A successful registration returns the Device ID, a short-lived device access
credential, a rotating refresh credential, and the existing per-device runtime
and WireGuard configuration.

### Refresh

~~~http
POST /v1/auth/refresh
~~~

The client signs the refresh request with its Device private key. A copied
refresh string alone is therefore insufficient to obtain a new access
credential.

Default refresh lifetime: 30 days.

Every successful refresh rotates the refresh credential. Reuse of an already
rotated refresh credential is treated as replay and revokes that refresh
family.

### Logout

~~~http
POST /v1/auth/logout
Authorization: Bearer <device-access>
~~~

Logout revokes the supplied refresh family and current session credentials
without revoking the Device identity itself.

### Device management

~~~http
GET  /v1/devices
POST /v1/devices/revoke
~~~

Device management requires a valid device-bound access credential and is
limited to Devices owned by the same User.

## Credential storage

Access and refresh strings are random opaque credentials. The Controller uses
their SHA-256 digests as lookup keys and does not persist the plaintext strings.

BP Connect stores the active access/refresh credentials together with its
Device private key in the existing protected local state. The password is not
stored.

## Prepared Windows client

Stage 3 prepared executables use bootstrap schema v3. A v3 executable contains
only the Device display name, Controller HTTPS URL, update-signing public key,
and optional legacy tunnel name.

It contains no password, user access credential, refresh credential, Device
private key, WireGuard private key, WGShim PSK, or one-time enrollment secret.

On first install the user enters username/password. BP Connect then registers
the new local Device and normally does not ask for the password again while the
refresh credential remains valid.

Bootstrap v2 and State v1 remain readable for Stage 2 migration compatibility.

## Future authentication methods

The design separates primary User authentication from Device registration.
Future methods can gate issuance of the same login-scoped credential without
changing the Device or transport model. Intended additions include TOTP,
Passkeys/WebAuthn, OIDC, and Authentik as an OIDC identity provider.

Those methods are not implemented in Stage 3.

## Security properties tested

The Stage 3 tests cover Argon2id hashing, absence of plaintext password storage,
generic invalid-login behavior, short-lived access expiry, hash-only credential
storage, Device private-key proof, refresh rotation and replay-family
revocation, User disable, Device revoke, the end-to-end HTTP lifecycle, revoked
Device re-registration denial, and Stage 2 bootstrap/state compatibility.
